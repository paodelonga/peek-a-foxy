# Security policy

## Supported versions

Peek-a-Foxy is pre-1.0. Only the latest release, and `main`, get security fixes.

## What this tool does that deserves care

- It installs a script that runs in Firefox's **privileged** browser context, through
  [fx-autoconfig](https://github.com/MrOtherGuy/fx-autoconfig). That is how every userChrome.js setup
  works, and it is by design: anything placed in the profile's `chrome/JS` folder runs with full
  browser privileges.
- It writes `config.js` and `defaults/pref/config-prefs.js` into Firefox's install directory. If that
  directory is not writable by you, it asks for rights: `sudo` on Linux and macOS, an administrator
  prompt (UAC) on Windows. In both cases the two files are checked against SHA-256 values pinned in the
  package, next to the fx-autoconfig commit, before they are copied: on Linux and macOS the very bytes
  that were checked are the ones handed to `sudo` (`sudo install` on Linux; `sudo tee` and `sudo chmod`
  on macOS, which has not been run on a Mac), and on Windows they travel in the command line of the
  elevated process, which checks them again. It never overwrites a different `config.js`.
- **On Windows the elevated process is the Windows PowerShell of the system folder**
  (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, a location that `GetSystemDirectoryW`
  reports and that is never taken from `PATH` or an environment variable), started with
  `-NoProfile -NonInteractive -EncodedCommand`. The script is generated by Peek-a-Foxy and carries the
  Firefox folder, the two files and their pinned hashes as literals; it uses only the language and .NET,
  so no module is loaded from a folder that you can write. It stops unless PowerShell is in its normal
  language mode, the hashes match, the folder is a Firefox folder (`firefox.exe`, `omni.ja` and an
  `application.ini` that names Firefox) and no link, junction, short (8.3) name or substituted drive is
  on the path; then it writes each file aside and renames it into place, and reports only through its
  exit code. The same route serves the standalone program and an installation with Python, so neither a
  Python installation nor the program itself runs with the rights you approve.
- **Residual risk of the Windows prompt.** The elevated process starts with the settings of your own
  account, so a program that already runs as you can still try to abuse the prompt you approve through
  what Windows and .NET read from those settings (for example environment variables that make .NET load
  a profiler into PowerShell). That cannot be removed from inside Peek-a-Foxy. A second, smaller gap:
  when the Firefox folder is writable by you but the direct copy still failed (a read-only `config.js`,
  a file held by an antivirus), a program of yours could in theory replace the `defaults` folder by a
  junction between the checks of the script and its writes; what could be written is limited to the
  fixed content of the two pinned files. None of this has been tried on a real Windows desktop.
- `FXAC_REPO` and `FXAC_COMMIT` replace the pinned fx-autoconfig and exist for tests. On Windows the
  elevated copy refuses them. On Linux and macOS the copy through `sudo` refuses them too, unless
  `--allow-unverified-loader` is given; the log then records that the copy was made without
  verification.
- It downloads fx-autoconfig with `git`, at a pinned commit, and refuses to continue if the checked-out
  commit differs from the pinned one.
- **The standalone Windows program and `install.ps1` (not published yet).** `install.ps1` is meant to be
  run as `irm https://github.com/paodelonga/peek-a-foxy/releases/latest/download/install.ps1 | iex`,
  which runs a script downloaded from GitHub at that moment, so it trusts GitHub and this repository's
  release; read the script first if that matters to you. It needs no administrator rights, changes only
  the folder it installs into, the user `PATH` and a temporary folder that it removes, and checks the program against a SHA-256 published
  next to it. That hash only catches a damaged or truncated download, because both files come from the
  same place and a replaced release would carry a matching hash. To check that the program was built
  by this repository's release workflow, run `gh attestation verify peek-a-foxy.exe -R paodelonga/peek-a-foxy`
  (build provenance signed through Sigstore, in a job apart from the build; not yet tried on a real
  release). The program is not code-signed yet, so Windows may warn about it. The Scoop and winget
  manifests that a release carries are templates with the version and the hash filled in; nothing has
  been submitted to Scoop or winget.
- `peek-a-foxy --install-completion` is the installer of Typer, the library behind the command line: for
  bash, zsh and fish it edits the startup file of your shell, outside the care that `install` takes with
  your files. For PowerShell it is refused, because Typer's installer first sets your execution policy to
  `Unrestricted` for your user; `peek-a-foxy --show-completion` prints the script instead, and you add it
  to your PowerShell profile yourself.
- It writes a local log (by default `~/.local/state/peek-a-foxy/` on Linux, `~/Library/Logs/peek-a-foxy/` on
  macOS and `%LOCALAPPDATA%\peek-a-foxy\logs\` on Windows; mode `600`) and, on request,
  the `peek-a-foxy doctor` report and the Firefox status file `chrome/peekafoxy-status.json`. Your home
  folder, user name, profile folder names and anything that looks like a token, a password or a
  credential in a URL are hidden before anything is written, printed or copied. Nothing is ever sent
  anywhere; you decide what to paste into an issue. The redaction is pattern based, so read a log or
  report before you share it.
- The supply chain of the project itself: every GitHub Action and every pre-commit hook is pinned by its
  full commit hash, no job keeps the token in `.git/config`, and the standalone program is built from a
  lock in which every file is hashed.

## What to report

Please report, for example:

- the installer writing or deleting files outside the profile and the Firefox install directory;
- a way to make the installer run unintended commands, or to install something other than the pinned
  fx-autoconfig commit;
- a way to make the elevated step (the `sudo` copy, or the PowerShell script of the Windows prompt) write
  anything other than the two pinned files into Firefox's folder, or write outside it;
- `install.ps1`, the standalone program or another file attached to a release doing something that its
  description does not say;
- a log, a report or the status file that shows what the redaction promises to hide;
- the script or the CSS exposing browser data, or loading remote code.

Not a vulnerability here: the fact that scripts in `chrome/JS` run with full privileges (see above), and
bugs in fx-autoconfig itself, which belong to [that project](https://github.com/MrOtherGuy/fx-autoconfig/issues).

## How to report

Use GitHub's private reporting: **Security > Report a vulnerability** on the repository page
(<https://github.com/paodelonga/peek-a-foxy/security/advisories/new>). Please do not open a public issue
for a vulnerability.

This is a small project maintained in spare time: reports are handled on a best-effort basis, with no
guaranteed response time.
